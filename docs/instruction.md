# Ommateum — Claude Code 開発指示書

## 1. 目的とコンセプト

macOS向けネイティブファイラー **Ommateum（オマティウム）** を開発する。

Ommateumは複眼を指す動物学用語に由来する。複眼が複数の個眼から構成されるように、複数のディレクトリを同時に表示し、素早く見渡せることをコンセプトとする。ただし、比喩をUI上で過剰に表現しない。

**最重要原則：Finderの使用感をできる限り損なわず、最小限の便利機能を追加する。**

主な差別化機能は次の3つ。

1. ファイル一覧の空白部分をダブルクリックして親ディレクトリへ移動。
2. VS Codeのエディターグループのように、タブのドラッグ＆ドロップによって縦横自由にペインを分割・再配置。各ペインが独立したタブを持つ。
3. QSpaceのように画面構成、ディレクトリ、タブを名前付きワークスペースとして保存・復元。

アプリ名の表記は **Ommateum**。内部プロジェクト名も `Ommateum` とし、リポジトリ名は `ommateum` を推奨する。Bundle Identifierは仮のものを設定可能とするが、実在の組織ドメインや開発者の識別子を勝手に確定しない。

## 2. 技術選定

- Swift + AppKitを基本とする。適切な箇所でSwiftUIを併用してもよい。
- macOSの公開・サポート済みAPIを最優先する。
- ファイル表示には `NSOutlineView`、`NSTableView`、`NSCollectionView`、`NSBrowser` などを比較検討する。
- ファイル操作では `FileManager`、`NSWorkspace`、`NSFileCoordinator`、Quick Look等を用途に応じて検討する。
- ペイン分割には `NSSplitView` などを検討する。
- 権限、ファイル監視、外部ボリューム、iCloud Drive、File Providerの扱いを設計に含める。
- 外部ライブラリは必要最小限とし、導入理由を記録する。
- Apple Silicon対応。対応する最低macOSバージョンは実装前に提案し、選定理由を記録する。

**Finderのファイル一覧そのものをアプリに埋め込めると決めつけない。** 公開APIで再利用できる範囲と、独自実装が必要な範囲を区別する。外観を似せることよりも、選択・フォーカス・キーボード・ドラッグ・ファイル操作の自然さを優先する。

## 3. ファイルブラウザ

Finderの基本動作にできるだけ近づける。

### 表示
- アイコン表示、リスト表示、カラム表示。ギャラリー表示は実現可能性を評価して段階実装する。
- ファイルアイコン、サムネイル、名前、サイズ、更新日時、タグ、隠しファイル表示、並べ替え、グループ化を適切に扱う。
- 大量ファイル時にもレスポンシブな表示を維持し、サムネイルやディレクトリ走査は非同期化する。
- タブごとにディレクトリ、表示モード、ソート・表示設定、戻る／進む履歴を保持する。

### 操作
- フォルダをダブルクリックで開く。ファイルをダブルクリックで既定アプリで開く。
- SpaceでQuick Look、Returnで名前変更など、Finderに沿うショートカットを採用する。
- ファイル選択、複数選択、範囲選択、ドラッグ＆ドロップ、コピー／移動／複製、ゴミ箱移動、Undo、競合時確認などを安全に実装する。
- Finderと差異が残る動作は明記する。ダミーのメニューや操作不能なUIは完成扱いしない。

### 空白領域のダブルクリック
- 一覧内のアイテム・ラベル・操作コントロールを除く空白をダブルクリックしたら、そのタブで親ディレクトリへ移動する。
- ファイル／フォルダのダブルクリック、選択、ドラッグ、スクロールバーなどと競合させない。
- リスト・アイコン表示等でイベントの対象判定を適切に行う。
- ルート、アクセス不可、親が存在しない場合は安全に何もしないか、適切に通知する。
- 設定から有効／無効を切り替えられるようにする。

## 4. Dropbox・Finder統合

ユーザーはDropboxデスクトップアプリを使用している。Finderの右クリックメニューに現れるDropbox独自の操作を、できるだけOmmateumでも利用したい。

ただし、Finder Sync拡張のコンテキストメニューを他のアプリがそのまま読み込めるとは**想定しない**。

まず次を調査・検証する。

1. DropboxのFinder Sync ExtensionやFile Providerとの関係。
2. 公開APIを通じてOmmateumで呼び出せるDropbox操作の範囲。
3. macOS Services／Quick Actionsなど、標準的に利用できる操作。
4. 代替策として選択ファイルをFinderで表示する機能の実装。

公開APIで不可能な機能を実現できると主張しないこと。非公開API、Dropbox内部実装の無断利用、不安定なハックに依存しない。技術的な制約と代替手段をドキュメントにまとめる。クラウドファイルのプレースホルダー、未ダウンロードのファイル、同期状態、権限を適切に扱う。

## 5. サイドバー

Finderに近い外観・操作感のサイドバーをウィンドウ左側に1つ設ける。分割ペインごとには設けない。

- よく使う項目、および利用可能な場所、外部ディスク、ネットワークボリューム、iCloud Drive、Dropboxなどを表示する。
- **理想はFinderのサイドバーと項目・順番・表示状態を同期すること。**
- ただし、Finderのサイドバー構成を安定して読み取る公開APIがあるとは仮定しない。お気に入りや順序の取得可否、変更検知、権限を検証する。
- 安定した同期が不可能な場合は独自サイドバーと手動編集機能を提供し、実現できた範囲・できない範囲を明示する。
- サイドバーからのナビゲーションは原則アクティブなペイン／タブに作用する。

## 6. 自由な分割とタブ

Ommateumの中心機能。VS Codeのエディターグループに近い体験を目指す。

### ペイン
- 1ウィンドウ内に任意の数のペインを配置できる。
- 左右、上下、ネストした分割（例：左1枚、右上下2枚）に対応する。
- 各ペインは独立したタブ群とアクティブタブを持つ。
- 各ペインの境界はドラッグでリサイズ可能。最小サイズを考慮する。
- フォーカス中のアクティブペインが自然にわかる控えめな表示を設ける。

### ドラッグ＆ドロップ
- タブを他ペインのタブバーにドロップすると、そのペインへ移動する。
- タブをペインの左／右／上／下端にドロップすると、対応方向に新規ペインを作る。
- ドロップ可能領域をドラッグ中にプレビューする。
- 同一ペイン内のタブ並べ替えに対応する。
- タブのドラッグとファイル項目のドラッグを混同しない。
- 最後のタブを移動／閉じた際の空ペイン除去と、分割ツリーの正規化を安全に処理する。

内部モデルは再帰的なSplit Tree（縦／横の分割ノード、Leafとしてペイン）など、状態保存が容易な設計を検討する。

## 7. ワークスペース

QSpaceのように、画面状態を名前付きで保存・復元する。

### 保存する状態
- ウィンドウの位置・サイズ。
- 分割ツリー、各境界のサイズ比率。
- ペイン数と配置。
- 各ペインのタブ構成と順序。
- 各タブで開いているディレクトリと表示モード。
- アクティブペイン／タブ。
- サイドバーの開閉・幅。

### 機能
- 名前を付けて新規保存、上書き、一覧表示、読み込み、改名、削除。
- アプリ終了時の通常セッションの自動保存と次回起動時の復元（無効化可能）。
- 存在しないフォルダ、取り外されたボリューム、権限を失ったURLはクラッシュせず処理し、復帰できるUIを提供。
- `Codable` + バージョン付きJSON等、読みやすく移行可能な保存形式を採用。
- 必要な場合はsecurity-scoped bookmarkを検討し、Sandboxの採否と整合性を保つ。

## 8. UI方針

- 無機質、簡潔、機能優先。Finderに近い標準的なmacOS UI。
- 標準フォント、SF Symbols、macOS標準ツールバー／コンテキストメニュー／サイドバーの表現を優先。
- ライト／ダークモードに対応。
- 独自デザインを過剰に追加しない。かわいらしい装飾や生物学モチーフをUI全体に持ち込まない。
- アイコンは将来的に個眼の幾何学的配置をモチーフにする余地があるが、**初期実装で凝った独自アイコンを必須としない**。
- キーボード操作、アクセシビリティ、フォーカスの挙動を重視する。

## 9. 品質・安全性

- ファイル操作でのデータ損失を防ぐ。破壊的操作には適切な確認とエラーハンドリングを行う。
- I/Oでメインスレッドを塞がない。ファイル監視により表示を適切に更新する。
- 大量ファイル、権限エラー、ファイル競合、名前変更、外部ディスク切断、クラウドプレースホルダー等をテストする。
- ネイティブアプリとしてビルドできるXcodeプロジェクトを維持する。
- 実装していない機能を完成済みとして示さない。

## 10. 作業の順序

### Phase 1: 技術調査・設計
最初に以下の可否を公開APIと実験で確認する。

- Finder風ファイルブラウザの標準UI再利用範囲。
- Dropbox右クリックメニューの再利用可能性。
- Finderサイドバーの項目・順序・設定の取得可能性。
- タブの移動と縦横自由なネスト分割の実装方法。
- Sandbox、ファイルアクセス、クラウドプロバイダとの互換性。

`docs/feasibility.md` に、検証方法・結果・制約・代替案を記録し、`docs/architecture.md` に選定した構成を記す。根拠のない仮定で先に進まない。ただし、制約が判明した場合も実現可能な代替策で開発を継続する。

### Phase 2: 単一ペインのファイラー
ファイル一覧、基本ナビゲーション、各種ファイル操作、Quick Look、空白ダブルクリックを実装する。

### Phase 3: タブと分割
ペインごとのタブ、ドラッグ＆ドロップ、分割・結合・サイズ変更を実装する。

### Phase 4: ワークスペース
レイアウト保存・読込、セッション復元、異常系処理を実装する。

### Phase 5: Finder統合・仕上げ
サイドバー、Dropbox対応可能範囲、操作感、アクセシビリティ、パフォーマンスを調整する。

## 11. 開発時の進行ルール

1. 最初にリポジトリと利用可能な開発環境を確認する。
2. 未決定の小さな詳細はFinder準拠・シンプルさ優先で合理的に決める。重大な仕様変更は理由と影響を明示する。
3. 各Phaseは小さな動作確認可能な単位に分けて実装する。
4. コード変更後は、環境が許す限りビルドとテストを実行し、結果を報告する。
5. 不可能な機能や未検証の機能は明確に区別し、代替案を記録する。
6. 設計と実装の状態をREADMEとdocsに反映する。
7. 計画書だけで止まらず、調査を踏まえて実際に動作するアプリを段階的に構築する。

**完成像：Finderの自然なファイル操作感を保ちながら、複数の場所を同時に見渡し、レイアウトを自在に保存・復元できるmacOSネイティブファイラー、Ommateum。**
